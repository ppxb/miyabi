# Miyabi 多来源刮削系统重构设计

2026-10-01。状态：单任务流程已实现，FANZA 正式接入为首选来源，保留 FC2 官方，JavDB 作为最终兜底；其他渠道继续逐个验证后再决定接入。

实施分支：`feat/scraping-refactor`，从已有功能所在的 `master` 创建，分阶段验证后再合回。

目标是让 Miyabi 独立完成影片识别、资料与图片获取、海报生成、演员资料、文件导出和 Emby 更新，用户不需要额外部署 MetaTube。以实际匹配准确率、资料完整度、图片质量与重复扫描成本验收，不以接入站点数量宣称替代完成。

## 已确定的产品边界

- JavDB 用作影片发现、搜索、订阅及关联入口，同时作为入库刮削的最后兜底来源。它的站点 ID 保留为外部身份，不承担统一刮削结果的身份。
- 来源接入以稳定性、身份准确性和图片实际可用性为准，不以数量为目标。解析器可运行或单个样本成功不等于完成验收；未通过验收的渠道不能作为正式支持来源默认启用。
- 入库刮削的标题、简介、演员、厂牌、系列、日期、评分、标签、封面和预览图由已启用的刮削来源提供。评分保留来源与原量表。
- 按用户最新确定的边界，探索、订阅及前端影片详情预览继续使用 JavDB。只有入库刮削才访问多来源；不为浏览列表或打开详情触发多源补全。
- 最新验收目标还包括：影片未被 JavDB 收录时，也能通过已确认的来源身份取得类似现有详情页的主体字段与图片。后续需提供来源无关的详情投影；浏览不能因此启动入库任务或无条件广播全部站点。当前前端按番号查询 JavDB 的实现尚未满足这一目标。
- 媒体库中的持久化刮削结果、后续文件导出与 Emby 使用同一份资料快照，来源缓存独立于媒体文件索引。
- 只知道番号的媒体文件也能进入刮削，JavDB 未收录不再成为刮削失败的前置条件。
- 所有需要生成的竖版海报都适用布局感知的构图策略，不按个别番号添加特例。有码横向封面默认按左右封套处理，无码、FC2 默认按完整单幅封面处理；来源明确的图片用途优先于影片类别。来源提供的正式海报和导入的自定义海报保留其构图。
- 首版专注自动识别、多源补全、自动选图与裁剪、失败重试和重新刮削。手动识别、指定单片来源、手动选图与裁剪暂缓，不预建对应接口、字段锁定或编辑界面。
- 磁力获取、115 离线下载和字幕服务保持独立职责；元数据来源的启用开关不隐式改变磁力来源选择。

## 主流程与职责

```text
         JavDB 影片入口 / 媒体扫描
                     ↓
                确认影片身份
                     ↓
             查询可用来源并校验候选
                     ↓
               合并资料、选择图片
                     ↓
               下载、检测、裁剪
                     ↓
               写出 NFO 与媒体附件
                     ↓
         提交资料、图片引用及 Emby 通知记录
                     ↓
                Emby 增量同步
```

单片业务阶段顺序执行，来源查询和不同影片可以有限并发。扫描索引、刮削任务和外部同步各自有明确的执行边界。实现使用普通 Go 函数和小接口，不引入通用工作流引擎、动态脚本插件或一套新的队列框架。

模块职责作为实现与审查约束：

| 模块 | 唯一职责 | 调用边界 |
| --- | --- | --- |
| `catalogue` | 发现、搜索、订阅及前端详情预览 | 保留 JavDB 外部关联，不反向调用入库刮削 |
| 来源适配器 | 获取并解析本站数据 | 返回来源结果；不依赖 Ent、任务队列、115 或 Emby |
| `metadata` | 将来源结果整理成可靠的统一资料 | 统一匹配、合并、来源缓存与图片候选选择，不导出文件或创建入库任务 |
| `library/scrape` | 执行单片刮削流程 | 顺序调用各阶段、检查文件来源、保存检查点与提交结果；不解析站点页面 |
| `image` | 将图片转换成可用的图像资产 | 解码、尺寸信息、去重、Pigo 构图和缓存写入，不决定影片身份或来源优先级 |
| `export` | 将确定的资料与资产写成媒体附件 | 生成 NFO、STRM 和图片文件，不发起刮削查询 |
| `emby` | 将已发布的媒体更新同步给 Emby | 消费持久化通知并独立重试，演员头像由元数据服务提供 |
| `tasks` | 调度与恢复任务执行 | 管理领取、运行、取消和完成，不包含站点或图片业务规则 |
| `app` | 装配依赖与生命周期 | 显式注册来源、建立依赖和启停服务，不承载刮削业务 |

`metadata` 内部的匹配、合并和选图优先使用可单独测试的普通函数。只有实际存在多实现或独立边界时才引入接口；不为每一个阶段建立管理器、仓储包装或空实现。

依赖沿流程向下传递。来源只返回标准化结果，不能反向调用编排器；共享实体模型不依赖具体来源。网络调用贯穿 `context.Context`，取消和超时能够传到站点请求。每种重试只由一个明确的层负责，避免来源、服务和任务三层重复重试同一次请求。

来源查询不要求拥有 115 会话，不写 STRM，不通知 Emby。前端详情继续使用 JavDB；下载入库图片或变更文件由刮削任务驱动。

## 身份与数据合并

每个实体有 Miyabi 内部身份，外部身份使用 `(provider, id)`。影片、演员、厂牌、系列和标签的来源 ID 不互相冒充，也不拼成假的 JavDB ID。演员不能仅凭同名自动合并；已有确认的来源映射和别名优先。

完整番号是影片匹配的主要线索，已有的番号规范化和候选降级规则继续复用。候选分组键只负责缩小搜索范围。来源返回的编号、来源 ID 或已确认别名必须支持同片判断，不能把模糊相似度最高的结果直接当作命中。某个来源存在歧义时跳过该结果，继续尝试其他已启用来源；全部来源仍无法确认身份时，以“无法唯一匹配”结束并保留具体原因，不强行合并或覆盖已有资料。

每个来源结果独立缓存，合并结果另有稳定的资料标识和所用策略版本。保留来源身份、更新时间、字段来源和所选图片，方便重试、重新合并及解释资料来自哪里。缓存数据与媒体库文件索引分别管理，清理媒体文件不应丢失来源匹配依据。

合并规则保持确定性：

1. 先筛除身份不相符或内容无效的结果。
2. 每个身份匹配层内按 FANZA、FC2 官方、JavDB 的顺序查询适用且启用的来源。标题、日期、时长、演员、厂商、标签、封面候选和预览候选齐全后停止查询；系列、导演、评分允许自然缺失，不为这些可选字段单独触发兜底。文字字段选取优先来源的有效值，后续来源只补缺。
3. 名单字段先按已确认身份去重，保留来源证据；不同版本、合集和单片不得混合演员名单。
4. 标签先做可解释的规范化和去重，不直接合并不同站点恰好相同的数字 ID。
5. 已验证主来源和补充来源仍未取得所需资料或可用图片时，才请求 JavDB 兜底。它不能覆盖优先来源已有的有效字段，也必须记录真实字段与图片来源；不能将兜底标成官方大图补全成功。JavDB 同样遵守身份校验，不以网络失败或来源缺失为由接受模糊匹配。
6. 兜底后必需资料仍无法取得时保留未完成状态和可重试原因，可选字段缺失明确展示。

## 图片策略

图片候选携带来源、用途、原始 URL 和实际尺寸。来源区分正式竖版海报、完整封面、背景图、预览图与演员头像，不能仅凭横竖比例猜测图片用途。

- 海报优先使用身份正确、分辨率足够的正式竖版图；需要生成时，先确定图片布局，再选择检测与裁剪区域。
- 来源明确标识的左右封套，只在原图右侧 55% 区域检测人脸，裁剪窗口也应约束在正封区域，避免封底剧照影响构图。检测区域缩小不改变输出使用原图像素的原则。
- 无明确布局信息时，有码横向封面默认使用左右封套策略；无码、FC2 默认使用完整封面检测和主体构图。类别来自可靠元数据，不维护单片番号特例；未知类别不因图片横向就强判为封套。来源明确的单幅图覆盖类别默认值，竖版图不套用横向封套规则。
- 右侧 55% 是封套的初始区域参数，并非所有图片的固定裁剪框。以真实封套、单幅封面、多人和主体靠边样本验证头部保留与封底排除效果，再确定参数。
- 清晰度主要看有效像素、裁剪后的可用尺寸和内容匹配，文件体积只作下载成本信息。
- 预览图取来源提供的原图地址，去除重复图片；不能把多组不同内容的预览图按序号强行对应。
- 一张图下载失败后尝试同片的下一候选；有其他合格候选时，单张坏图不使整片失败。
- JavDB 图片只在其他来源的封面均不可下载或解码时使用。若资料阶段尚未请求 JavDB，图片阶段会按已确认番号单独查询兜底；图片与新增的 JavDB 身份写入同一恢复检查点，最终随影片发布事务提交，不覆盖主来源标题和演员。非兜底候选内部仍按实际有效像素比较。
- 当前接受来源提供的低分辨率可解码图片，不将其自动视为下载失败。低清原图仍可能生成低清海报，不把 mediumUrl 回退宣称为高清补全。
- 来源适配器负责必要的 Referer、Cookie、CDN 或图片解码差异；复用现有代理和受限下载能力，不在界面暴露可任意代理的远程 URL。
- 检测只使用缩小副本，输出取原图。模糊或遮挡人脸可能无法检测，此时按图片用途采用确定的默认构图，不阻断刮削任务。
- 图片按内容去重并保存不可变缓存；所有未完成任务的图片检查点参与保留引用计算。

图片候选选择与 Pigo 构图是两个独立步骤。来源图本身不清晰时，调整裁剪不会生成真实细节；不把放大尺寸视为获取高清原图。

## 可恢复性与性能

- 每部影片一条持久化刮削任务，保存已确认身份、资料结果、图片检查点和完成标记；重试复用成功阶段。
- 同一影片的写入任务互斥，防止查看详情、重新刮削、定向扫描和普通扫描互相覆盖。
- 每个来源共享限流和超时控制，单片查询及全局并发都有上限；不对每部影片无条件广播全部站点。
- 已知来源 ID 直接查详情。按来源能力、已确认身份和缺失字段决定后续查询，减少无效检索。
- 同一来源、同一查询的并发请求合并；重复刮削共享来源缓存。来源设置变化后重新组合结果，尽可能复用仍有效的来源缓存。
- “未找到”与网络错误分别处理；短期缓存确定的空结果，网络故障不永久记录成不存在。
- 网络、检测、编码和文件准备都在数据库写事务外进行。只在新缓存图片获得持久引用的短阶段持有图片保护锁。
- 导出失败不会把数据库标记为成功；数据库提交失败后可以重试发布。影片资料、最终图片引用、完成标记及 Emby 通知记录一起提交。
- Emby 不可用由通知队列重试，不重新检索或裁剪整部影片。头像和字幕等补充失败应有独立、可恢复的结果。
- 普通扫描跳过资料、文件和图片策略均未变化的影片；提供“重新刮削资料”和“重新生成海报”的明确操作。

性能验收记录冷缓存与热缓存的请求数、单片耗时分布、内存峰值、来源限流次数和全库重复扫描成本。先以现有实现作基线，不能仅依据 goroutine 数量宣称高性能。

每阶段交付都检查实际收益：热缓存刮削不重复访问来源，同片并发请求只产生一轮抓取，失败恢复不重做成功阶段，无变化重扫不重新下载和裁剪。并发必须受全局与来源两级限制，慢来源不能无限延长单片任务。批量读取、短事务和已验证的图片保护机制继续保留，不以重构为由退回逐行查询或长时间持锁。

## 设置与操作界面

刮削设置独立于 JavDB 的发现线路设置。当前展示 FANZA、FC2 官方、JavDB 的用途与启停开关，顺序固定为首选、对应类别来源、最终兜底；前后端都禁止将 JavDB 提到前面。连接状态展示及其他配置按后续实际需要接入。

初期以“影片资料与图片来源”和“演员资料与头像来源”两组设置承载差异，不开放逐字段权重编辑器。GFriends 作为头像来源复用，不伪装成完整影片元数据来源。

配置保存后生效。已进入持久化阶段的任务使用启动时的选择快照，后续任务使用新设置；停用来源会阻止新的抓取，不直接删除已导出图片。用户可明确选择是否按新来源重新刮削现有影片。

前端影片详情继续使用 JavDB。媒体库卡片始终可以打开详情弹窗：已有 JavDB ID 时直接读取，无 ID 时在用户点击后按番号匹配 JavDB；匹配失败在弹窗中说明并允许重试，不把本地影片 ID 当作 JavDB ID，也不因浏览触发多源刮削。刮削任务保留来源身份与字段来源，失败可重试；重新刮削资料和重新生成海报的独立操作后续接入媒体库。后台错误需要定位到具体来源或阶段。

手动识别、手动选图和手动裁剪作为后续独立功能评估，不纳入本期实施与验收条件。

## 来源验收与选择

已删除 AVBase、MGStage、JavBus 的刮削适配器、对应测试及设置入口。JavBus 磁力功能独立保留，FC2 的现有可用实现保留。按照 MetaTube 的渠道逐个验证并精选，不再维护一张承诺全部接入的来源清单。

| 来源 | 当前状态 | 下一验收边界 |
| --- | --- | --- |
| FANZA | 已注册为首选来源，GraphQL 检索、批量身份核对、详情与图片下载完成；正式适配器通过四部真实影片验证 | 历史商品搜索覆盖、低清封面、预告片 403 仍是来源限制；详见 [验证记录](fanza-verification.md) |
| FC2 官方 | 保留现有适配器，在售页面曾解析成功 | 尚需完整的商品、图片、下架与失败行为验收，不将单样本成功视为全面通过 |
| JavDB | 发现、订阅及前端预览继续使用，已接入资料和封面的最终兜底 | 复用已有 ID、查询缓存与图片下载能力；番号匹配层由 metadata 统一控制 |
| GFriends | 保留现有演员头像职责 | 后续从 Emby 同步中拆出选图职责 |

先验证少数必要渠道能完成日系影片与 FC2 的完整流程，已有渠道覆盖足够时不继续扩张。每个正式来源都需要覆盖完整番号、格式等价、易混淆番号、缺字段、下架、限流、超时、验证页面和解析变化；网络故障不能缓存成不存在。真实站点验收必须包含详情、封面与预览图实际下载、解码、有效分辨率和身份核对，不能只凭首页可达、图片 URL 存在或 HTTP 200 判定成功。记录样本范围、网络条件、日期、失败率和冷/热缓存耗时，通过后才启用。

## 实施顺序与完成条件

1. **身份与任务主干**：补齐来源身份模型，把单片 `scrape` / `cover` 合并成一个可恢复流程。同步修改任务统计、重试、缓存清理、扫描收尾和通知提交；通过现有扫描、裁剪、导出和恢复回归。
2. **可运行的多源流程**：接入首批真实来源及设置页，从扫描到合并资料、图片下载、入库、Emby 导出完整打通。独立来源必须能在没有 JavDB 元数据的情况下完成工作。
3. **资料完整度与刷新**：补演员身份、头像、多源预览图、来源说明、失败重试、重新刮削资料和重新生成海报。
4. **覆盖与性能验收**：对真实片库中的有码、无码、FC2、多人、缺图、下架、同名演员及多分段影片验证；以统一样本比较 MetaTube 的匹配、完整度、图像效果和耗时。

本次按新数据结构和新任务流程直接实现，不兼容或迁移旧刮削数据、旧检查点与旧任务；不保留双轨运行分支。开发和验收使用新建数据库，删除旧的生产数据不属于代码重构操作。

只有来源启停、无 JavDB 元数据刮削、资料/图片/演员自动补全、歧义处理、新任务的失败恢复以及 Emby 更新均通过验证，才能宣布用户在已覆盖片库的自动刮削场景中不再需要 MetaTube。只抽取接口或增加来源开关不算完成；旧数据兼容和手动纠正能力不属于本期范围。
